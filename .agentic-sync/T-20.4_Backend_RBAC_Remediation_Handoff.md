## 1. Resumen Ejecutivo (El "Por Qué")
Durante la regresión J-04 (T-20), se aisló la causa raíz de los fallos E2E en Playwright. Tras corregir las URIs (T-20.1) y erradicar los Timeouts de la UI (T-20.2 y T-20.3), los tests siguen fallando porque **la capa de red del Backend rechaza las peticiones con códigos HTTP 403 (Forbidden) y 500 (Internal Server Error)**. 
Específicamente, las llamadas a los endpoints de `Kill-Switch`, `Workdesk` y `Kanban` carecen de la resolución correcta de Roles (RBAC) o Tenant en el `SecurityContext` del entorno E2E (Zero-Mock). El objetivo de este handoff es depurar y estabilizar la capa de autorización en el Backend para permitir que el E2E fluya de manera nativa.

---

## 2. Definición de Hecho (DoD - AP-02)
- ✅ Se identifican y corrigen las inconsistencias de inyección de Roles / Tenant en el `IdentityService` o `SecurityFilterChain` que causan los 403/500 durante las llamadas E2E.
- ✅ Los controladores de negocio (ej. `WorkdeskController`, `TaskController`, `SessionRevocationController`) resuelven correctamente el contexto de seguridad del usuario de pruebas.
- ✅ Ley Global 3 (Trazabilidad): Los cambios en Backend incluyen el comentario `// @Traceability: Retro-Remediación RBAC J-04 (T-20.4)`.
- ✅ El código compila nativamente (`mvn clean compile`) sin regresiones.
- ✅ Commit bajo estándar convencional: `fix(security): resolucion de autorizacion rbac para e2e zero-mock [T-20.4]`

---

## 3. Contexto Mandatorio (ADRs y Leyes Globales)
*   **Zero-Mock V2 Protocol:** Está ESTRICTAMENTE PROHIBIDO implementar "mocks" duros en el código productivo para bypassear la seguridad. Si el test E2E falla por permisos, el usuario en Base de Datos (Liquibase E2E) debe tener los roles, O el interceptor JWT debe parsearlos correctamente. No apagues la seguridad.
*   **Ley Global 3 (Trazabilidad):** Todo cambio debe estar trazado.

## 5. Plan de Acción (Action Plan)
1.  **Auditoría de Intercepción:** Revisa cómo se están inyectando y evaluando las anotaciones `@PreAuthorize("hasAnyRole(...)")` en los endpoints afectados.
2.  **Verificación del Contexto E2E:** Asegúrate de que el filtro JWT (`JwtAuthenticationFilter` o similar) o el `IdentityService` estén decodificando correctamente los roles del token o buscándolos en la DB para inyectarlos en el `SecurityContextHolder`.
3.  **Remediación Segura:** Aplica la corrección lógica. Asegúrate de que el Tenant y el Role se resuelvan determinísticamente para el usuario de los tests de Playwright sin comprometer la seguridad productiva.
4.  **Compilación y Commit:** Verifica que el proyecto compila tras tus cambios y realiza el commit documentado.

---

## 6. Estrategia de Testing (Validación)
-  **Compilación Host:** `mvn clean compile` debe ser exitosa.
-  **Prueba Unitaria/Integración Local:** Validar mediante las pruebas de integración del backend (`IdentityGovernanceIntegrationTest` o equivalentes) que un token simulado con los roles correctos obtiene un HTTP 200 en lugar de un 403.
